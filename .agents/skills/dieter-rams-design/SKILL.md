# Dieter Rams Design

Read [Dieter Rams principles and philosophy](references/principles-and-philosophy.md) before substantive work at the start of each portfolio app-work conversation. Read it again after a material revision or if lost from context; otherwise reuse the loaded reference. This startup read applies even when a task has no visible interface change. For unrelated work, apply only the useful general principles; do not invent a design review.

## Establish the actual task

Identify the product, user outcome, current revision and approved identity. Read its current AGENTS.md/CLAUDE.md, adopted Apple/portfolio standards and relevant product profile. Treat Rams as a discipline for judgement, not a replacement brand or a source of platform requirements. Preserve newer explicit owner decisions, accessibility, truthful state and domain rules. Do not impose Braun styling, a monochrome palette, smaller text, hidden navigation or a universal spacing ratio.

## Make the design decision

1. State the user's job and the present obstacle in one sentence.
2. Identify the smallest complete improvement. Reuse a sound existing component before adding another mode, panel, control or AI interaction.
3. Apply relevant R01–R10 checks in the reference. Inspect the real flow and states, not just a polished screenshot.
4. Explain meaningful trade-offs. Keep a useful feature, revise a weak approach or remove unnecessary work; do not agree with a proposal simply because it was suggested.
5. Implement authorised work and verify its actual effect. Preserve input, history, orientation and recovery paths.

For interface work, inspect hierarchy, labels, shared gutters, type roles, optical alignment, kerning at the rendered size, contrast, touch/focus targets, long content, enlarged text and supported appearances. Use the product's approved geometry and platform guidance; Rams specified no universal pixel values, typeface or kerning formula.

For AI and agent work, keep capability limits visible, expose the actual action and its outcome, make stop/cancel reliable, and keep manual routes available where the product requires them. A new model or animation is useful only if it improves the user's task. Do not claim these software rules are Rams quotations.

For backend or release work, assess relevant clarity, reliability, durable data, truthful completion, maintainability and resource use. Mark visual checks outside scope rather than pretending a source test proved appearance or usability.

## Review proportionately

Use [the review checklist](references/review-checklist.md) for material feature or design decisions. For a small fix, record the applicable IDs and focused evidence in the existing work record. Do not add a new approval ceremony or a parallel release gate solely because this skill was loaded.

Separate PASS, FAIL, UNVERIFIED and NOT_APPLICABLE. A passing script cannot establish beauty, discoverability or physical feel. Retain revision, environment and actual evidence for each claimed result. Prefer existing meaningful tests and inspect affected consumers; do not manufacture a numeric design score or checklist-only tests.

Deliver the concrete outcome, why it helps, verification and remaining material gaps. Keep the startup acknowledgement brief and avoid repeating the principles in routine responses. Never claim that publishing a skill forces all chats to read it: only a configured host/project route can request that, and active or disconnected conversations may not load new instructions.
